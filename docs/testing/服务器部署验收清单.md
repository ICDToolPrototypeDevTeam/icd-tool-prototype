# 服务器部署手工验收清单

适用：`docker compose -f docker-compose.server.yml up -d` 单端口、三服务（redis / backend / worker）部署形态。
前提：浏览器访问 `http://<服务器>:<端口>/`，**不允许**通过 SSH 查看容器日志。
产物前提（**开始验收前先确认**）：本清单验的是**本次提交的构建产物**。该部署形态下页面来自宿主 `frontend/dist`（`docker-compose.server.yml` 把它只读挂载为 `/app/static`），后端与 Worker 来自 `icd-tool-backend-v4.0` 镜像，队列来自 `redis:7-alpine` 镜像（该编排文件**无 `build` 段**，镜像在外部构建后 `docker load`）。因此开始前必须：① 在仓库根重新构建前端产物 `cd frontend && npm run build`（覆盖 `frontend/dist/`）；② 重新构建后端镜像（本机仓库：`docker compose -f docker-compose.yml build backend`），按 `部署说明.md` §3 重新导出 `icd-tool-backend.tar.gz` **与 `redis-7-alpine.tar.gz`** 并在服务器 `docker load`（§5.2）；③ `docker compose -f docker-compose.server.yml up -d`。**跳过 ①②** 会验到上一版前端产物或旧镜像（如 Worker 因 redis-py 版本不匹配起不来）。

| 1 | 打开首页，查看顶栏 | 出现「MOCK 模式」开关；顶部无警示条 | |
| 2 | 打开 MOCK 开关 | 全站顶部出现橙色警示条；刷新页面后开关仍为开启 | |
| 3 | 关闭 MOCK 开关提交一次正确性分析，再打开开关提交第二次（**允许两次重叠运行**：运行参数按各任务提交时的快照隔离，重叠不会再互相改写） | 两次的日志面板首行（时间列**之后**的文本列）均以 `===== 任务开始 task=correctness mock=False/True (来源: 前端参数)` 开头（`mock=` 随开关变化；该行其余部分为 `resumed=` 与本次 `job_id`，随任务变化）；每次紧随其后的一行以 `[config] USE_MOCK_LLM=` 开头，且**两次提交完全相同**（该行其余部分为 `(容器配置)` 字面量、三个模型的 Key 有无、`JUDGE_PROVIDERS`、`OUTPUT_DIR`、`STATIC_DIR`；其值为容器 `.env` 原值，本仓库出货值为 `0`）。首行随开关变、`[config]` 行不变 —— 这两行的关系就是「开关覆盖了容器配置」的证据：**关闭开关的那次任务按真实模式运行；打开开关的那次任务按 MOCK 运行**（后者的结果页证据见第 9 行） | |
| 4 | 处理中展开「执行日志」 | 面板每 3 秒轮询一次后端日志，有新输出即出现；每步结束有 `[timing]` 耗时行（单个 Case 的判官调用可能数十秒无新输出，这不等于面板失效） | |
| 5 | 处理中点「终止任务」 | 按钮变「正在终止…」；任务在**当前步骤或当前 Case 结束时**变为 `canceled`（解析阶段已按行间隔检查、秒级响应；正在飞的模型调用需等本次返回）；输出目录文件**未被删除**。若点击发生在最后一个检查点之后，任务会正常跑完而不是 `canceled`，属预期 | |
| 5b | 用一个大输入文件提交任务，在**上传/提交尚未返回**的那几秒内观察处理页；任务创建完成后再看一眼 | 提交窗口内页面上**没有**「终止任务」按钮（此时点击无人接收，故干脆不显示）；任务创建完成后按钮才出现 | |
| 6 | 把一个纯文本文件（例如 `.txt`）改名为 `publisher.xlsx`，与一个正常的 HLR 文件一起提交一次正确性分析 | 任务创建成功但很快失败；错误页显示分类「文件无法解析」+ 建议；点「复制诊断信息」后按钮变「已复制」，**并且真的粘贴一次**：文本以 `===== ICD 工具诊断信息 =====` 开头、含 `任务 ID:` 与 `失败分类:` 行（明文 HTTP 下走 `execCommand` 兜底，必须实测粘贴目的地真的有内容）；若按钮变为「复制失败：请手动全选下方文本」，下方必须出现只读文本框，点进去应自动全选、手动复制能得到同样内容；连续点击两次时，「已复制」应在**第二次**点击后约 3 秒才复位 | |
| 7 | 把容器 `.env` 里**三个** API Key（DeepSeek / MiniMax / Qwen）**全部**改成无效值，然后 `docker compose -f docker-compose.server.yml up -d` 重建容器使 `.env` 生效，再提交一次正确性分析（HLR 需含 **≥4 个会进入判官的 case**，即 ≥4 条能匹配到 ICD 的需求；请用条数较多、且与 ICD 匹配较多的样例文件） | 任务运行到判官阶段后失败；错误页显示分类「所有模型服务均不可用」，而不是笼统的「处理失败」。注意：把一个 Key 改成**非空的无效值**（例如写入 `bad-key`）不会失败 —— 另两个模型仍能判定，任务会正常 `completed`（多模型兜底的既有行为，本项不验收该情形）；但把某个 Key **清空**（留空字符串）会以分类「服务配置缺失」整体失败，属预期而非缺陷 | |
| 8 | 提交一次任务，待其进入「处理中」后重启**后端**容器（`docker compose ... restart backend`），再打开该任务 | **Celery 模式**：任务**继续运行**（执行在 worker 容器），状态仍为「处理中」；日志面板继续增长（来自 worker 写的 `job.log`，API 增量同步）；任务最终正常完成。**重启前已完成的任务不在列表中，属预期** | |
| 8b | 继续上一步，向上滚动日志面板 | 只能看到重启前日志的**尾部**（最多 256KB / 2000 行）；更早的行不恢复，属预期而非缺陷 | |
| 8c | 提交一次任务，待其进入「处理中」后重启 **worker** 容器（`docker compose ... restart worker`），再打开该任务 | 任务短暂显示「处理中」，心跳超过 300 秒后由 API 巡检标为「已中断」；日志保留。点「继续」能按原参数续跑并最终完成（已落盘的解析产物与 LLM 缓存被复用） | |
| 8d | 在任务「排队中」（见第 12 行）时重启**后端**容器 | 任务仍为「排队中」，Worker 随后照常领取并执行，最终「已完成」；不需要重新上传 | |
| 9 | MOCK 开关开启状态下跑完一次任务 | 结果页顶部出现「本次任务运行于 MOCK 模式」提示 | |
| 10 | 关闭 MOCK 开关后回看第 9 步的结果页 | 提示仍在（该提示取自任务自身记录，不随开关变化） | |
| 11 | 展开「执行日志」面板，查看时间列 | 面板上有「时间列为 UTC」的标注；时间列的值与服务器本地时间可能相差数小时，属预期（该列与 `job.log` 中可 grep 到的字符串一致） | |
| 12 | 把根目录 `.env` 的 `ICD_WORKER_CONCURRENCY` 临时设为 `1` 并重建 Worker（`docker compose -f docker-compose.server.yml up -d worker`），然后**连续提交两个**正确性分析（第二个在第一个跑完前提交） | 第二个任务显示「任务已排队，等待 Worker 执行…」，不显示步骤进度；第一个任务结束后第二个**自动开跑**（标题变为步骤进度）；两个任务终态均为「已完成」，结果可正常查看与下载。验完把并发恢复为 20 并再次 `up -d worker` | |
| 13 | 继续上一步：在第二个任务仍显示「已排队」时，点它的「终止任务」 | 立即变为已终止（**无需**等第一个任务结束）；错误页提供「继续执行 / 放弃」，点「放弃」结束该任务；Worker 取到该消息时会校验控制面并跳过执行（该任务日志可读到跳过原因） | |
| 14 | 提交一次正确性分析，待其进入「处理中」后点「终止任务」并等待 | 任务在检查点停止并落「已终止」；输出文件不删除；可「继续」或「放弃」。Worker 日志出现任务结束记录，进度不再前进 | |
| 15 | 提交一次正确性分析，待其进入「处理中」后使用强制终止（前端的强制终止入口；或 `POST /api/v4/jobs/{id}/cancel?force=true`） | 任务立即落「已终止」；Worker 日志出现 `Terminating ... (9)`；任务不会自行恢复为「处理中」 | |
| 16 | 依次检查三个容器 | `docker compose ... ps` 中 redis 为 healthy、backend 与 worker 为 running；`docker compose ... logs worker \| grep concurrency` 显示 `concurrency: 20 (prefork)`（若按内存公式调小则为对应值）；`docker compose ... exec redis redis-cli ping` 返回 `PONG` | |
| 17 | 上传一个超过 50 MB 的单文件 | 请求返回 413（页面提示文件过大）；`backend/output/v4/` 下不留下不完整的任务目录（`.part` 临时文件不残留） | |

第 3 行的判别点是**两行的关系**，与 `.env` 取何值无关：`[config]` 行是进程启动时的快照（等于容器 `.env` 原值），`任务开始` 行由前端每次提交时显式给出。所以 `.env` 为 `1` 时，关闭开关会让两行**不同**（`mock=False` 对 `USE_MOCK_LLM=1`）；`.env` 为 `0`（本仓库出货值）时，打开开关才会让两行**不同**。只要偏移方向与 `.env` 取值一致，就说明开关真的生效了。另：`(来源: 前端参数)` 表示这次提交带了显式参数（本工具前端**总是**显式提交 `use_mock_llm=true|false`）；若看到 `(来源: 继承容器配置)`，说明该任务不是从页面提交的。
第 6 行不能用「不上传 Publisher/Subscriber」来验收：未选择任何 EoICD 文件时，前端会在提交前 `alert` 拦截、服务端也会以 422 拒绝，任务**不会被创建**。「输入文件缺失」这个分类只在「任务运行期间输入文件消失」时才可能出现，浏览器可达路径里没有这个动作 —— 不要把它当作可复现的分类去验收。
第 7 行的「≥4 个判官 case」是**实测阈值**决定的：每个模型需**连续 3 次**判定失败才被标记为不可用，因此前 3 个 case 只是在累积计数，直到第 4 个 case 开始时才会抛出该分类。注意判官 case 不等于 HLR 需求条目：只有「已匹配」与「待确定」的需求会进入判官，「无匹配」的需求直接跳过 AI、不计入 case（`backend/app/v4/matching/reverse_case_builder.py:63-67`），故需 **≥4 个会进入判官的 case**，即 ≥4 条能匹配到 ICD 的需求。若 case 数不足，任务可能跑完而不报此分类 —— 那是样例不足，不是缺陷；换用与 ICD 匹配更多的样例即可。
第 12 行把 `MAX_CONCURRENT_JOBS` 临时设为 `1` 是为了稳定复现排队 —— 默认上限 2 时需同时有 3 个任务在跑才会看到排队；验收完成后按需改回 `2` 并重建容器。
