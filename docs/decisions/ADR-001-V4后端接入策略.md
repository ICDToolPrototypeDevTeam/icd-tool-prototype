# ADR-001 V4 后端接入策略

| 项目        | 内容                              |
| --------- | ------------------------------- |
| 状态        | **Accepted**                    |
| 生效范围      | 后端（V3 / V4）                    |
| 提议日期      | 2026-07-27                      |
| 影响 Issue   | 「V4.0 后端工程化集成」                |
| 待更新文档路径范围 | 项目顶层 `docs/`，非 `_v4_backend_raw/docs/` |

> 本 ADR 与 `CLAUDE.md` / `.claude/rules/context-rules.md` / `.claude/rules/documentation-rules.md` / `.claude/rules/debug-rules.md` 同级生效；作为后续 V4.0 工程化集成的事实源。

---

## 背景

主仓库 `main` 分支已发布 V3.0 release（chunk-level 多智能体 + Python 硬规则评分 + 4 份 Word）。
组员在本地分支 `_v4_backend_raw/` 完成了 V4.0 脚本后端（反向管线：HLR→EoICD + 多 Agent 裁判 + Review 共识 + 1 份共识 Word / 1 份 xlsx / 3 份单模型 Word）。

当前需将 V4.0 工程化集成到 FastAPI 入口，但不得破坏 V3.0 既有 API 与前端。

V4.0 与 V3.0 在以下方面存在显著差异：

1. **输入边界**：V3 用 EoICD Word + Excel；V4 用 EoICD Pub/Sub Excel + HLR Word。
2. **输出文档命名**：
   - V3 走 `EoICD条目化需求.docx` / `EoICD与软件高层需求差异报告.docx`
   - V4 走 `EoICD条目化清单.xlsx` / `EoICD与HLR一致性分析报告_*.docx` / `EoICD与HLR多模型共识分析报告.docx`
3. **评审范式**：V3 用 CrewAI 双模型 chunk-level 择优；V4 用脚本匹配 + 多 Agent panel + Review 共识。
4. **LLM 真实可用情况**：V3 的 MiniMax / DeepSeek 真实可用；V4 当前 DeepSeek 真实、MiniMax / Qwen 仍是 mock 回落（来自 `_v4_backend_raw/backend/app/llm/factory.py:57-59`，本 Issue 不改 V4）。
5. **已知代码缺陷**：`_v4_backend_raw/backend/app/pipeline.py` 缓存路径存在 `FileNotFoundError` Bug（结构梳理报告已记录，本 Issue 不动；由独立 Issue 处理）。

---

## 决策

### D1：V4.0 作为后续后端主线流程

V4.0（含反向管线、多 Agent 面板、Review 共识）作为后续后端主推流程；V3.0 chunk-level 流程在 V4 稳定后另开 Issue 评估下线。本 ADR 范围内**不删除 V3 模块与路由**。

### D2：V3.0 旧 API 暂时保留，本 Issue 不删除

- 全部 V3 路由维持现状：
  - `GET  /api/health`
  - `POST /api/eoicd/analyze`
  - `GET  /api/jobs/{job_id}`
  - `GET  /api/jobs/{job_id}/result`
  - `GET  /api/jobs/{job_id}/outputs/requirements`
  - `GET  /api/jobs/{job_id}/outputs/minimax-requirements`
  - `GET  /api/jobs/{job_id}/outputs/deepseek-requirements`
  - `GET  /api/jobs/{job_id}/outputs/difference-report`
- 前端 V3 适配在本 Issue 不动，由前端 Issue 单独跟进。
- V3 业务模块（`backend/app/crew/`、`backend/app/merge/`、`backend/app/scoring/`、`backend/app/docx/` 等）保留不动。

### D3：V4.0 新接口统一走 `/api/v4`

V4 全量路由挂载 `/api/v4` 前缀；与 V3 在 URL 命名空间上完全隔离。两套响应 Pydantic 类互不 import。

V4 路由：

```text
POST /api/v4/coverage-analysis
GET  /api/v4/jobs/{job_id}
GET  /api/v4/jobs/{job_id}/result
GET  /api/v4/jobs/{job_id}/outputs/eoicd-xlsx
GET  /api/v4/jobs/{job_id}/outputs/consistency/{model}    # {model}=deepseek|minimax|qwen
GET  /api/v4/jobs/{job_id}/outputs/consensus-docx
```

### D4：V4.0 第一版工程化集成阶段保持原版业务逻辑不变

V4.0 后端以下模块在本 Issue **一律不改写**：

- `app/parsers/`（EoICD 解析规则、HLR 解析规则）
- `app/matching/`（含 candidate_matcher、unified_matcher、reverse_matcher、signal_profiler、hlr_classifier、entry_filter、eoicd_enricher、hlr_labeler、reverse_case_builder 等；包括 7 维评分权重）
- `app/comparison/`（含 case_builder、semantic_judge、multi_judge、review_agent、report_generator）
- `app/prompts/*.md`（forward_judge / reverse_judge / consensus 等提示词模板）
- `app/doc_generators/`（excel_generator / word_generator / consensus_word_generator；含报告 word / excel 内容结构）
- `app/llm/`（factory / deepseek_client / mock_llm；含 mock fallback 行为）
- `app/config.py` 中除"环境加载块"以外的常量（属性中英映射表、匹配权重、属性类别映射等）

本期仅做工程化包装：

- FastAPI 路由；
- 上传保存与文件名校验；
- Job 管理（共享 `JobManager`，按 `job_kind` 分发）；
- `output_dir` 路径适配；
- 文件下载（仅 3 类对外：xlsx / 单模型 word / 共识 word）；
- Docker Compose 启动；
- `requirements.txt` / `.env.example` 更新（占位 Key 形如 `sk-your-key`，不写真实 Key）；
- 最小异常处理。

### D5：当前 DeepSeek 为主要真实模型；MiniMax/Qwen 仍为 mock，必须显式标识

- API **不写死 DeepSeek**：`/outputs/consistency/{model}` 路由保留 `deepseek|minimax|qwen` 扩展点。
- V4 的 `factory.py:57-59` 对 `minimax` / `qwen` 仍返回 `MockLLMClient`；该行为由 V4 代码决定，本 Issue 不修改 V4。
- API 层强制要求 `V4JobResultResponse.mock_models: list[str]` 与 `V4JobStatusResponse.mock_models: list[str]` 显式标识当前实际参与且为 mock 的 provider。

**`mock_models` 取值规则**（核心）：

```text
sources  = multi_judge_results_json["providers"]   # V4 实际跑过的 provider 名单
mock_only = {"minimax", "qwen"}                    # V4 当前事实：这两个仍走 mock
mock_models = [p for p in sources if p in mock_only]
```

**关键约束**：本规则**只列本次实际参与且为 mock 的模型**；不要在用户只请求 `["deepseek"]` 时把 `["minimax","qwen"]` 写进 `mock_models`（无意义的"占位 mock"会污染前端展示）。

**特例**：`use_mock_llm=1` 时，`factory.py:38-40` 把所有 provider 强制走 `MockLLMClient`，deepseek 实际也是 mock；此时 sources 内全部 provider 一律进 `mock_models`。

**前端必须遵守**：`mock_models` 非空项对应的下载按钮 / 报告文案须显式提示 `[mock]`，不要与真实模型结果混读。

**本期不涉及**：单模型 word 顶部是否加 mock 水印——属于 `doc_generators/word_generator.py` 修改，由后续 Issue E 处理；本 ADR 不决定。

### D6：API 保留 `consistency/{model}` 扩展点，以支持后续真实多模型或 CrewAI 编排

- 路由模板：`/api/v4/jobs/{job_id}/outputs/consistency/{model}`；`{model}` 当前 ∈ `{deepseek,minimax,qwen}`，未来加入 `openai|claude|crewai_panel|...` 不需改 URL 形态。
- 路由层做白名单校验（避免任意值进入 IO 路径）；不匹配名单返回 `400`。
- 是否引入 CrewAI 作为上游编排在 `CrewAI 工程化集成 Issue` 中再决策；本 ADR 不假设。

### D7：JSON 中间产物不作为正式下载 API 暴露

不暴露的 JSON：

- `reverse_matches.json`
- `multi_judge_results.json`
- `consensus_results.json`
- `reverse_report.json`

这 4 个 JSON 保留在 `job_dir/output/` 内部，用于：

1. 服务端日志佐证；
2. **FastAPI 层反读 `multi_judge_results.json.providers` 计算 `mock_models`**（D5 关键数据源）；
3. 运维 / 调试问题定位。

未来若需公开 JSON 下载，应通过后续 Issue 加 `Accept: application/json` 内容协商或新开子路由，不在本 ADR 中固化。

### D8：JobManager 共享，但路由层按 `job_kind` 分发

- 单一模块级 `job_manager` 实例（与 V3 共享）；
- `Job` 实例新增内部字段 `kind: Literal["v3","v4"]`，默认 `"v3"`；
- V3 路由只读 V3 kind 的 Job；V4 路由只读 V4 kind 的 Job；**跨版本查询返回 `404` + 提示用户改用正确前缀**；
- `kind` 字段**不进任何对外响应 schema**，仅作路由层分发依据；与 D2（不污染 V3 schema）和 D3（V3/V4 命名空间隔离）共同保证版本隔离。

---

## 原因

- **D1**：V4 已通过 `_smoke2` 端到端测试（exit 0；12 份产物落盘；6 份原始 JSON + 5 份 Word + 1 份 xlsx），主线流程证据更充分。
- **D2**：CLAUDE.md §11.2 规定 Claude Code 不主动删除 V3 / 关闭 Issue / 改 PR；前端解耦是独立 Issue。
- **D3**：清晰命名空间隔离降低回归风险，前端按版本切换；响应 Pydantic 类互不 import，避免响应 schema 互相污染。
- **D4**：本期为工程化移植而非业务重构；V4 各模块都已有原版测试样例，重写风险远大于包装收益。
- **D5**：V4 当前事实约束；同时 mock 不应被前端误以为是真实结果；规则以"实际跑过 ∩ 是 mock"取交集而非硬编码列表——避免用户只请求 deepseek 时被错误告知"minimax 是 mock"，降低沟通成本。
- **D6**：URL 形态稳定，便于未来真实接入或编排策略升级时 API 不需反复破坏；路由层白名单防止 path traversal。
- **D7**：暴露 JSON 会让 API 表面持续膨胀；JSON 已落盘，运维调试足够；mock_models 仍可在 API 层反读得到。
- **D8**：避免引入"两套 JobManager"导致代码重复；但又必须保证 V3/V4 响应 schema 隔离，所以加内部 `kind` 字段而非双 JobManager 实例。

## 影响

### 后端代码改动（小范围）

- 新增模块：`backend/app/api/v4/` 路由模块；含 V4 FastAPI handlers、Pydantic schema、文件保存与下载帮助函数。
- `backend/app/models.py`：新增 `V4JobStatusResponse` / `V4JobOutputs` / `V4JobResultSummary` / `V4JobResultResponse` 4 个 Pydantic 类；**V3 已有 Pydantic 模型保持原样不修改**。
- `backend/app/main.py`：增加 V4 路由与 background thread 调度；与 V3 路由并存；通过 `job_kind` 校验做版本分发。
- `backend/app/job_manager.py`：新增 `kind` 内部字段；扩展 `create_job(kind="v3"|"v4")` 参数；已有 `Job.update` / `get_job` 行为不变。

### 后端代码改动（V4 内部，不写）

以下模块位于 `_v4_backend_raw/backend/app/`，在本 Issue 工程化集成后建议搬运到 `backend/app/v4/`，**但不改写其内容**：

- `app/v4/parsers/`
- `app/v4/matching/`
- `app/v4/comparison/`
- `app/v4/prompts/`
- `app/v4/doc_generators/`
- `app/v4/llm/`
- `app/v4/config.py`（环境加载块除外；其余常量按 D4 不改写）

### 配置 / 文档改动

- `backend/.env.example`：新增 V4 相关项说明（`JUDGE_PROVIDERS`、`USE_MOCK_LLM`、`DEEPSEEK_*`、`MINIMAX_*`、`QWEN_*`）；占位 Key 仅写 `sk-your-key`，**绝不写真实 Key**。
- `backend/requirements.txt`：视 V4 依赖情况补项（如 `python-multipart` 等）；尽量复用现有项。
- `docs/architecture/api.md`：新增 §13 V4 章节；JSON 下载段不写。
- `docs/project/scope.md`：输入边界段更新为 V4 形态；明确 V3 旧边界不在本 Issue 删除。
- `docs/project/workflow.md`：以 V4 主力反向管线为主线重写；V3 列为附录。
- `docs/architecture/current-architecture.md`：模块职责表更新；V4 子模块挂 `backend/app/v4/` 命名空间。

### 容器 / 部署

- `docker-compose.yml` / `Dockerfile`：微调；新增 `output_v4/` 挂载；启动命令保留同一 `uvicorn app.main:app`。

### 前端

- 本 ADR 不影响前端；前端需根据 `docs/architecture/api.md` 单独 Issue 适配 V4 上传与下载 UI。

### 不动 `_v4_backend_raw/`

本 ADR 与后续工程化集成 Issue 一律**不修改 `_v4_backend_raw/` 下任何文件**。该目录仅作为 V4 事实源保留；迁移完成后由专门 Issue 评估删除时机（本 ADR 范围外）。

## 替代方案

| 方案                                                            | 不选择理由                                                              |
| ------------------------------------------------------------- | ----------------------------------------------------------------- |
| 在 V3 入口上"挂 V4 handler"而不新加路由                                  | 路由前缀与响应 schema 难以区分；违反 D3                                     |
| 直接替换 V3 入口（V3 → V4 全量升级）                                     | 与 D1 / D2 冲突；删 V3 与本期原则不符                                     |
| 把 V4 `PipelineResult` Pydantic 模型扩展为含 `mock_models` 等字段         | 与 D4 冲突；让 API 层反读 `multi_judge_results.json` 更轻便                 |
| 抽离 V4 业务逻辑到独立 Python 包                                         | 与 D4 冲突；工程化集成阶段原版位置即是事实源                                  |
| 在 `consistency/{model}` 之下再放 CrewAI 编排产物                      | 与 D6 冲突；当前未引入 CrewAI，URL 形态提前预留即可                       |
| 始终把 `["minimax","qwen"]` 写进 `mock_models`（不论本次是否实际调用）          | 与 D5 "实际参与" 语义冲突；用户已显式要求只列本次实际参与的 mock                |
| 修改 `_v4_backend_raw/backend/app/pipeline.py` 缓存路径 Bug 在本 Issue 一起修 | 与 D4 冲突；bug 修与工程化包装解耦，分别由独立 Issue 处理                    |
| 把 `_v4_backend_raw/` 的 V4 业务模块直接以原路径挪进 `backend/app/`（不新建 `v4/` 命名空间） | 与 V3 同名模块冲突风险高（parsers / llm / pipeline / doc_generators 等同名）；命名空间隔离更稳  |
