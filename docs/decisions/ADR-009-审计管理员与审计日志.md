# ADR-009 审计管理员与审计日志

| 项目 | 内容 |
| --- | --- |
| 状态 | **已接受**（已实施，待服务器验收） |
| 生效范围 | 认证角色模型；业务 / 管理 / 审计接口准入；操作日志；系统运行监控页；MongoDB 集合 |
| 提议日期 | 2026-11-13 |
| 关联 ADR | ADR-007（用户登录与账号隔离，本 ADR 在其上扩展角色）；ADR-008（Celery + Redis 执行层，本 ADR 读取其指标）；不改变评分体系、输出文档格式与既有业务 API 路径 |

---

## 背景

ADR-007 落地后，系统只有「普通用户 / 管理员」两种身份（`is_superuser` 布尔）。面向内网约 20 个账号开放后，用户提出两类新需求：

1. **审计可追溯**：需要查看业务用户的登录与操作记录，也需要查看系统管理员的登录、操作记录；日志信息项要全面（IP、时间、操作人、操作内容、操作模块、操作类型、结果等），支持按信息项查询，内容对非技术审计人员可读（英文 / 代码翻译为中文）。
2. **运行状态可见**：需要查看各人员正在使用的进程、内存等状态，用直观图表反映系统当前运行情况。

这两个需求都要求「第三方监督视角」：审阅者必须能看到管理员干了什么，因此审阅者不能是管理员本身。原有的 `is_superuser` 二值模型无法表达这一职责分离。

## 决策

### D1：角色从布尔值扩展为三值 `role`

- `role: 'user' | 'admin' | 'auditor'`，默认 `'user'`；中文标签为「业务用户 / 系统管理员 / 审计管理员」。
- `is_superuser` 保留为兼容字段，由 `role` 派生并同步（`admin` → True，其余 → False），历史账号 `role` 为空时按 `is_superuser` 回退（`effective_role`），启动时 `ensure_user_roles()` 回填落库。
- 用户管理接口接受 `role`；旧字段 `is_admin` / `is_superuser` 继续兼容，冲突时返回 422；不允许把最后一个启用状态的管理员降级（409）。

### D2：职责分离——系统管理员不能进入审计中心，审计管理员只能使用审计中心

- 系统管理员：拥有全部业务权限与账号管理权限，访问 `/audit/*` 与审计页面统一 403。
- 审计管理员：**只**能访问 `/auth/login`、`/auth/logout`、`/auth/me`、`/health` 与 `/audit/*`；业务接口统一 403，前端登录后只能进入审计中心。登录后的 `/auth/me` 仍可用，用于前端获取自身身份与渲染页面。
- 已知并接受的后果：系统管理员也无法查看「系统运行状态」页（该页属于审计中心）。

### D3：审计日志落 MongoDB `audit_logs`，异步批量写入、fail-open

- 新集合 `audit_logs`，字段覆盖：时间（UTC）、类别、模块、动作、动作类型、结果、操作人（账号 / 角色）、IP、客户端、请求方法与路径、对象类型 / ID / 名称、详情键值、错误信息、耗时、检索文本。
- 写入由后台 `AuditWriter` 完成：有界队列（20000）+ 批量 `insert_many`（100 条 / 0.5s 刷盘）。队列满或 Mongo 异常时丢弃并记日志，**不影响业务请求**。
- 不记录密码、JWT / Cookie、API Key、文件内容；登录失败对客户端统一返回 400，具体失败原因只写入审计记录。

### D4：审计内容中文化

- 模块、动作、动作类型、角色、结果、任务类型、controller profile、模型名等代码值统一在 `app/audit/catalog.py` 维护中文词表；
- 记录时同时写入代码值与中文标签，前端直接显示中文标签；检索文本包含中文标签与详情值，支持中文关键词查询；
- User-Agent 解析为「Chrome 120 / Windows」形式的人类可读客户端描述。

### D5：系统运行监控采用容器级 + 任务级指标，不挂载 `docker.sock`

- **API 容器**：进程内每 5s 采样 cgroup 内存与 CPU，写 Redis `icd:metrics:api`（TTL 30s）。
- **Worker 容器**：Celery Worker 后台线程每 5s 上报 `icd:metrics:worker:{hostname}`（TTL 20s）；心跳超过 15s 视为失联。
- **任务进程**：Worker 认领任务后上报子进程 PID，审计接口按 `psutil` 读取 RSS / CPU，按用户聚合运行中任务数、总内存与总 CPU。
- **趋势**：采样点进 Redis `icd:metrics:history`（720 点 / 1 小时 TTL），供折线图；Redis 不可用时返回 `available=false` 与提示。
- **依赖**：Mongo / Redis 只做连接与延迟探测。
- 不挂载 `docker.sock`、不采集宿主机级进程与整机资源，避免给容器增加主机控制面权限。

### D6：容器级告警阈值固定，任务级指标仅展示

- 内存 ≥ 75% 告警、≥ 90% 严重；CPU ≥ 85% / 95%；磁盘 ≥ 80% / 90%；Worker 心跳 > 15s 失联；Redis / Mongo 不可用为严重。
- 任务进程的 RSS / CPU 只展示，不设阈值（单任务内存取决于输入文件与模型，无稳定基线）。
- 阈值在代码中集中定义，v1 不提供页面配置。

### D7：审计日志永久保留，v1 不提供删除与导出

- 无删除接口、无 CSV 导出；查询审计日志本身不记入审计（避免读操作自放大日志量）。
- 时间为存储 UTC、展示 Asia/Shanghai；IP 取 `request.client.host`，暂不解析 `X-Forwarded-For`（部署在反向代理后时需后续增加可信代理配置）。

## 原因

1. **监督独立性**：审计管理员如果同时是业务管理员，就无法审计管理员自身操作；角色三值与访问互斥是满足「可查看系统管理员日志」的前提。
2. **不阻塞业务**：审计写库是旁路能力，Mongo 抖动不应让上传、轮询、下载失败，因此选择有界队列 + fail-open。
3. **可读性**：原始代码值（如 `task_cancel`、`reverse`）对审计人员不可读，词表 + 中文标签 + 中文检索文本把翻译成本前置一次。
4. **安全边界**：挂载 `docker.sock` 等于把宿主机控制权交给 Web 容器；容器级 cgroup 采样 + `psutil` 子进程足以回答「谁在跑、占多少内存」，风险与收益更平衡。
5. **兼容成本低**：`role` 是新增字段，旧账号通过 `effective_role` 回退与启动回填兼容，`is_superuser` 继续派生，不破坏现有管理接口。

## 影响

### 数据与依赖

- MongoDB 新增集合 `audit_logs`（6 个索引）；`init_beanie` 的 `document_models` 增加 `AuditLog`。
- 审计日志随业务量增长，永久保留；原型阶段不引入归档 / TTL，后续如需可按 ADR 增补。
- 审计查询依赖 MongoDB；Mongo 不可用时查询返回 503，业务侧审计写入被丢弃（fail-open）。

### API 与前端

- 新增 `GET /api/v4/audit/logs`、`/audit/logs/{id}`、`/audit/meta`、`/audit/overview`、`/audit/system`、`/audit/system/history`，全部仅审计管理员可访问。
- 业务接口统一挂 `require_business_access`：审计管理员访问业务接口 403。
- `/auth/me` 与用户管理响应增加 `role` / `role_label` / `is_auditor` 字段；旧字段保留。
- 前端新增 `/audit` 页面（概览 / 登录日志 / 操作日志 / 系统运行四个标签页），图表用纯 SVG / CSS 实现，不引入图表库；登录后按角色跳转。

### 部署

- 无新增容器、无新增环境变量与端口；新增第三方 Python 依赖 `psutil>=6.1,<8`（容器与任务进程的 RSS / CPU 采集），需**重建后端镜像**才生效。
- 本地 compose 未设置内存上限时，内存百分比为空，只显示已用字节；服务器部署需通过 compose 限额获得百分比。

### 不变

- 既有业务 API 路径与字段不变（仅权限语义收紧：审计管理员不可访问业务接口）；
- 反向 / 正向管线、评分规则、输出文档格式不变；
- 任务状态语义（ADR-008）不变。

## 替代方案

1. **继续用 `is_superuser` 布尔值 + 前端隐藏**：无法表达第三方审计角色，管理员可绕过前端直接调接口；审计管理员与管理员权限无法互斥。否决。
2. **审计日志写文件（JSONL）**：查询需要全量扫描与自建索引，分页、关键词、聚合都要手写；Mongo 已是必需依赖，直接落库成本更低。否决。
3. **同步写审计日志**：实现简单，但 Mongo 抖动会拖慢或阻塞业务请求，违背旁路原则。否决。
4. **挂载 `docker.sock` 读取全主机容器与进程**：能获得宿主机视角，但把主机控制面暴露给 Web 容器，安全风险远超原型需求。否决。
5. **引入 Prometheus + Grafana**：监控能力完整，但需要额外容器与配置，且审计人员需要的是内嵌页面而非外部系统。否决。

## 状态

已接受，已在本分支实施并完成本地 Docker Compose 验证：三角色权限矩阵（管理员访问审计 403、审计管理员访问业务 403、审计接口 200）、登录失败与设置变更审计记录、日志查询 / 明细 / 概览 / 系统运行 / 趋势接口、前端构建通过。浏览器内的视觉渲染效果尚未做自动化验证，需人工检查；服务器部署验收待进行。
