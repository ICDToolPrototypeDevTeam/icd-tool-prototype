## 背景

### v1 方案

V4 五星评价体系 v1 在 2026-08-23 提议，核心设计：
- 5 档：full+strong=5★ / full+moderate|weak=4★ / majority+strong|moderate=3★ /
  majority+weak=2★ / split|single_source|no_consensus=1★
- evidence_alignment 由 review LLM 自评（strong/moderate/weak），后端按 3 子维度
  （Coverage/Consistency/Quality）综合映射
- 2★ 触发复查

### v1 暴露的问题（来自真实 LLM 跑 `故障注入1.0.docx`）

1. **strong 门槛过低**：3 维度 criteria 中 `consistency=2` 只要求「结论一致 + 各自引用字段」，
   导致绝大多数 case 都被判为 strong，**moderate/weak 几乎不出现**
2. **5★/4★/3★ 边界语义错位**：2★ 只是「majority + weak」，没解释为什么需要复查；
   4★/5★ 仅靠 evidence 强弱区分，含义单薄
3. **4★ → 5★ 升级路径断裂**：复查机制仅触发 {1, 2}，4★ 不进 re-review；而 4★ 的
   「evidence 弱」本质上是 analysis 文本笼统，无法靠自然重判修复

实测结果：跑 `故障注入1.0.docx` 真实样例发现——**只触发 5★ 和 3★，1★/2★/4★ 全部不触发**。

### v2 设计动机

按 agreement_level 分档（full/majority/split）+ 字段类型（key/non_key/vague）
**单维度**区分：

| 档 | 触发条件 |
|---|---|
| 5★ | full + 无字段不一致 |
| 4★ | full + 任意字段不一致（key 或 non_key 或 vague） |
| 3★ | majority + 无 key 字段分歧 |
| 2★ | majority + 有 key 字段分歧（触发复查） |
| 1★ | split / single_source / no_consensus |

字段分类：
- **关键字段 (key, 12 个)**：Direction / DataFormatType / BitOffset / ParameterSize /
  OneState / ZeroState / Label / FuncRngMin / FuncRngMax / **Units / Period / SDIExpected**
- **对比字段 (non_key)**：DefaultValue / InitValue / Range / Interval
- **模糊表达 (vague)**：未提具体字段名（「covered」「一致」等），不影响降级

### v2 暴露的问题（来自真实 LLM 跑 `故障注入1.0.docx`，2026-08-26）

v2 删除 `inconsistent_attributes` 并把其语义改写为「provider 间字段级分歧」，
但这两者是**不同的事实**：

- Word 报告「判断」列大量显示「不一致」，而「不一致属性」列显示「—」——
  因为 3 个 provider 对同一 EoICD-HLR 差异往往**共识识别**，按 v2 规则不进
  `field_disagreements`，于是渲染源为空。
- 「HLR 与 ICD 不符的是哪个属性」是报告的核心交付内容，不能依赖 provider 是否分歧。

### v3 fusion 设计动机

拆成两个正交维度，各管各的：

| 维度 | 描述什么 | 判定规则 | 输出位置 |
|---|---|---|---|
| `agreement_level` | 3 个 provider 对该 case 判断的一致性 | **v0 语义规则**（看 analysis 语义，不只看字面 coverage_status） | JSON + 报告「共识」列 |
| `inconsistent_attributes` | HLR 与 ICD 实际不符的 EoICD 属性 | **不管 provider 是否一致**，只要 HLR/ICD 不符就记录 | JSON + Word「不一致属性」列（**主字段**） |
| `field_disagreements` | 3 个 provider 对同一字段给出不同判断 | 仅当 provider 对同字段值/判断不同时记录 | **JSON only**（辅助字段，不渲染） |

星档映射规则**直接复用 v2**（agreement + field_disagreements 是否含分歧）。

## 决策

引入 **5 星评价体系 v3 fusion（两维度并行）**，核心变更：

1. **恢复 `inconsistent_attributes`**（语义回到 v0/v1）：EoICD-HLR 事实差异清单，
   结构为 `{attribute, detail, providers}`，用于 Word 报告渲染
2. **保留 `field_disagreements`**（v2 设计不变）：provider 间字段级分歧，
   结构为 `{field, category, providers, values, detail}`，**仅入 JSON**
3. **`agreement_level` 用 v0 语义规则判定**：不同措辞表达相同判断视为一致；
   相同措辞表达不同判断视为分歧
4. **两字段完全独立、不互斥**：同一 case 可同时有两者
5. **`evidence_alignment` 保持删除**（v2 已删）
6. **星档由后端计算**：`_map_star_rating(agreement, field_disagreements)` 逻辑不变
7. **复查触发不变**：`star_rating ∈ {1, 2}`

### 5 档映射规则（v3 fusion，复用 v2）

| 星级 | agreement_level | field_disagreements 中是否有 key 字段 | final_coverage_status |
|---|---|---|---|
| 5★ | full | 无（field_disagreements 为空或仅含 vague）| majority coverage_status |
| 4★ | full | 有（任意 category）| majority coverage_status |
| 3★ | majority | 无 key 字段（含 non_key 或 vague 或空）| majority coverage_status |
| 2★ | majority | 有 key 字段 | majority coverage_status |
| 1★ | split / single_source / no_consensus | (any) | 待确认 |

注意：
- **5★ 严格档**：full + **完全无字段不一致**（vague 也不影响——vague 表示没引用字段名，
  不能算"不一致"）
- **4★ 退一档**：full + 任意字段不一致（即使仅 non_key）
- **3★ 多数 OK**：majority + 少数意见仅涉 non_key 或 vague
- **2★ 需复查**：majority + 少数意见涉及关键字段（Direction / DataFormatType / Units 等），
  与复查触发条件 `{1, 2}` 天然对齐；display 取 majority coverage_status（多数 provider
  的判断仍有效，少数反对意见由 `field_disagreements` 承载，不丢信息）

### 字段分类与检测规则（v3 fusion）

`inconsistent_attributes` **不分类**——事实差异必然引用具体属性名。
`field_disagreements` 按下述三档分类 `category`。

review LLM 扫描 3 个 provider 的 analysis 文本，两路并行提取：

1. **EoICD 与 HLR 的事实性不一致**（如 3 个 provider 都看到「ICD=19 Bits vs HLR=17 Bits」）
   → 进 `inconsistent_attributes`（**不管 provider 是否共识**）。
2. **裁判间意见分歧**（如 provider A 判 Direction 已覆盖，B 判不一致）
   → 进 `field_disagreements`，并按 key / non_key / vague 分类。

同一字段可以同时出现在两个列表里（共识识别出差异，但对是否标 inconsistent 看法不一）。

**关键字段白名单（12 个，category: "key"）**：

```
Direction         信号方向（send / receive）
DataFormatType    数据类型（UnsignedInteger / Float / Boolean 等）
BitOffset         位偏移
ParameterSize     参数位宽
OneState          布尔状态语义（如 OPEN / CLOSE）
ZeroState         布尔状态语义（如 FALSE / TRUE）
Label             信号标识符（Label 号或信号名）
FuncRngMin        功能范围下限
FuncRngMax        功能范围上限
Units             单位（m/s、℃ 等）
Period            周期
SDIExpected       SDI 源
```

**对比字段白名单（category: "non_key"）**：
DefaultValue / InitValue / Range / Interval

**模糊表达（category: "vague"）**：
未提具体字段名（如"covered"/"一致"/"覆盖完整"）——**不影响降级**

### 数据契约（v3 fusion）

```python
class InconsistentAttribute(BaseModel):
    """EoICD-HLR 事实差异（主字段，渲染到 Word 报告）。"""
    attribute: str                                   # EoICD 属性名（如 "Direction"）
    detail: str = ""                                 # 一句话说明不一致内容
    providers: list[str]                             # 识别出该差异的 provider（审计用）

class FieldDisagreement(BaseModel):
    """provider 间字段级分歧（辅助字段，仅入 JSON）。"""
    field: str                                       # 字段名（如 "Direction"）
    category: Literal["key", "non_key", "vague"]    # 字段类型（ADR-004 v2/v3）
    providers: list[str]                             # 涉及哪些 provider
    values: list[str]                                # 各 provider 给出的值
    detail: str = ""                                 # 一句话说明

class ConsensusResult(BaseModel):
    # 5★/4★/3★/2★/1★ 映射逻辑见 _map_star_rating
    agreement_level: str                             # v0 语义规则判定
    star_rating: int                                 # 1-5
    inconsistent_attributes: list[InconsistentAttribute]  # v3 fusion 恢复（主字段）
    field_disagreements: list[FieldDisagreement]     # v2 保留（辅助字段）
    # evidence_alignment: 已完全删除（v2 起）
```

注意 JSON key 命名差异：`inconsistent_attributes` 用 `attribute`，
`field_disagreements` 用 `field`。

### 复查升星路径（v2）

| 当前 | 复查后可达 | 路径逻辑 |
|---|---|---|
| 1★ | 2★ | peer-aware 后，原本 split 的 3 provider 形成 majority |
| 2★ | 3★ | minority provider 重新审视反对方 key 字段意见 → 弱化立场 |
| 4★ | 5★ | **理论路径**——复查触发集合仍仅 `{1, 2}`，4★ 不进 re-review；4★ → 5★ 仅在 natural retry + provider 主动补充具体字段引用时发生 |

### 降级 cap（不变）

| 存活 provider | cap |
|---|---|
| 0 | 1★ + no_consensus + 待确认 |
| 1 | ≤1★ |
| 2 | ≤2★ |
| 3 | 不限制（不加 confidence cap） |

## 原因

- **5 档粒度对齐复查语义**：v2 的 2★ = "少数意见涉及关键字段" → 与 re-review 触发条件
  `{1, 2}` 天然对齐；4★ = "全一致但有字段争议"，明确指出"需要审查细节"
- **单维度字段类型分类**：v1 的 evidence_alignment 3 子维度（Coverage/Consistency/Quality）
  在真实 LLM 上门槛失真；v2 简化为"是否有 key 字段分歧"一个维度，配合 LLM 扫描字段
  引用的明确任务，输出稳定性更高
- **5★ 真正代表"完美"**：full + 无字段争议 = 真正可采纳
- **5 档分布均衡**：5★/4★ 配对（full 档）+ 3★/2★ 配对（majority 档）
- **LLM 任务简化**：从"3 维度综合映射"变成"字段冲突检测 + 字段类型分类"——更直接、更可验证
- **breaking change 明确**：v1 的 evidence_alignment 字段信息密度低（被 strong 噪声淹没），
  删除不会丢失有意义的语义；保留 v1 字段会带来向后兼容包袱

## 替代方案

### 方案 A：保留 v1 evidence_alignment 多维度方案（仅优化 strong 门槛）

调整 Coverage/Consistency/Quality 子维度阈值，可能改善 moderate/weak 占比。
**否决**：根本问题在 3 子维度综合映射本身——LLM 难以稳定给出 3 子维度评分；
v2 的单维度字段检测更直接。

### 方案 B：保留 3 星体系，仅扩展 final_coverage_status 维度

3 档粒度粗，无法区分「全一致 + 无字段争议」与「全一致 + 有字段争议」。
**否决**。

### 方案 C：5 星 + confidence 数值阈值（confidence 0.85 强 / 0.60 弱）

LLM 给 confidence 的标准不明确；用户明确指出「confidence 是 AI 给的，给分规则不明确」。
**否决**。

### 方案 D：5 星 + 字段不一致驱动单维度映射（采用）

`_map_star_rating(agreement, field_disagreements)` 仅看是否有 key 字段分歧；
LLM 任务简化为字段冲突检测与分类。**采用**。

### 方案 E：v2 单字段方案（field_disagreements 兼作报告渲染源）

用 `field_disagreements` 同时承担「EoICD-HLR 事实差异」与「provider 间分歧」两种语义。
**否决**：两者是不同事实，共识识别的差异会被规则排除在外，导致报告「不一致属性」列
大面积为空（2026-08-26 真实样例实证）。
