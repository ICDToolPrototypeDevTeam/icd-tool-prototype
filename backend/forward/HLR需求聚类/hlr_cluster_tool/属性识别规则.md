# 属性识别规则说明

本工具把软件高层需求（HLR）中的需求条目，按"需求文本里明确提到的接口属性"聚类。
判断"提到某属性"靠一组正则特征，规则如下。**原则：只认需求文本，不读、不匹配 ICD/EoICD 接口文件。**

## 一、检测范围（口径）

### 0. 只从表格取（文档级口径）

**只从 docx 的表格解析需求，表格之外的正文段落一律不参与任何提取。**

很多需求文档（FGMC 这类尤其明显）在需求表格前后有大段说明性正文——"范围""术语和定义""缩略语"
"设备概述""软件概述"，以及每个需求表格前的小标题（如"ARINC 输出 SSM 标准""左翼燃油温度"）。
这些文字里也会出现总线名、信号名（FGMC 正文就写了 CAN / ARINC429 / RS422 和多路信号），
但它们**是文档说明，不是需求条目**，不应参与聚类。因此解析器只走表格，段落文字只用于审计记录。

表格本身也要过滤，跳过的表格连同原因写进输出的 `meta.skipped_tables[]`（含 `table_no` /
`reason` / `preceding_text` —— 即表格前最近的文字 / `desc`），便于回答"某条需求为什么没出现"：

| 跳过原因 | 判据 | 例 |
|---|---|---|
| 非需求表（无"需求编号/需求ID"字段） | 表格没有需求编号字段 | FGMC 的"术语/缩略语"表；HSCU 的"标签总览"表 |
| 需求编号为空或为 N/A 占位 | 有字段但值为 N/A | FGMC ID=1759/1784/1036 三张"是否为需求=否"的说明表 |
| "是否为需求"为否 | 该字段值为 否/N/No/False/0 | 同上（两条件互为补充） |
| 空表 | 无键值对内容 | HSCU 末尾空表 |

> 实测：FGMC 12 张表 → 跳过 5 张（术语、缩略语 + 3 张 N/A 说明表）→ 得 7 条需求；
> HSCU 12 张表 → 跳过 2 张（标签总览、空表）→ 得 10 条需求。

### 1. 表格内的检测范围

分两类，口径不同：

| 内容 | 检测范围 | 原因 |
|------|----------|------|
| **属性类判定**（23 个属性） | **整条需求表格的相关字段**：`需求中文` 优先，其余非元数据字段（基本原理/验证方法/实现方法/**注释**/输入数据…）一并扫描 | 量程、单位、分辨率等信息常写在"基本原理""注释"里，只读正文会漏 |
| **身份信息**（bus/label/bit/name/direction） | **只认"需求中文"** | 身份是需求对信号本身的描述；若并入其他字段，会被别的字段的总线字样污染（如模拟量需求"从ADCINA3接收"被基本原理/验证方法里的 A429 字样带成 A429） |

每条属性证据标注来源字段（`[需求中文]`/`[基本原理]`/`[注释]`），便于人工核对；
`meta.detection_fields[]` 列出**该文档实际参与检测的全部字段**——排查"这条属性从哪来"时先看这里。

**元数据字段不参与检测**（按**命名规则**判定，兼容各系统字段名差异）：
字段名含 `ID`、以 `是否` 开头、或含 `安全`/`衍生`/`对象类型`/`来源` 的，都视为需求管理信息，不扫描。

> 早年这里是硬编码清单（`{需求ID, 对象类型, 是否衍生, 安全相关}`），AMS 叫"安全相关"能排除，
> FGMC 叫"**是否安全性相关**"就漏掉了、被当普通字段扫描。改为命名规则后两边都能覆盖。

> **不再从段落解析"章节标题"**：早期版本会把 `5.2.5.2.3、xxx` 这类章节标题作为 `section` 带出来，
> 但它属于"表外正文"，现已整体移除——解析器只产出表格字段。

## 二、属性识别规则表

23 个属性全部有识别规则，覆盖情况如下（属性名与 `eoicd_crop.yaml` 一致）：

| 属性类 | 触发条件（需求表格文本中出现） | 示例 | 正则要点 |
|--------|---------------------------|------|----------|
| Label | **只认数字 label 号** | "解析L36"、"LABEL126"、"Label114"、"标号126" | `L(?:ABEL)?\s*\d{1,3}` / `标号\d+`。名称型助记标签（`LBL_*`）**不归入本类** |
| BitOffsetWithinDS | 提到 bit 位，且方向为**发送/写入** | "向429发送…L214的bit16至bit28写入"、FGMC"第14到29位发送…" | 出现位段（`bitN` / `第N位`）且 direction=TX |
| BitOffsetWithinMsg | 提到 bit 位，且方向为**接收/解析** | "从A429接收数据中解析L36，bit13至bit28" | 出现位段（`bitN` / `第N位`）且 direction=RX |
| RefreshPeriod | "以X为周期"、"每X秒/毫秒解析\|发送\|采集"、"周期" | "以1000ms为周期"、"每1秒解析" | `以\d+ms…周期` / `每\d+…` |
| TransmissionIntervalMinimum | "以X为周期发送"、"最小发送间隔X" | "最小发送间隔1000ms" | 发送周期特征 |
| ActivityTimeout | "活动超时（按/为）X" | "逻辑端口活动超时按3000ms处理" | `活动超时…\d+ms` |
| PublishedLatency | "（消息）发布时延（不超过/上限为）X" | "发布时延不超过2000ms" | `发布时延…\d+ms` |
| SamplePeriod | "每X采样"、"采样周期" | "每250ms采样一次" | `每\d+ms…采样` |
| MessageSize | "消息长度X字节" | "消息长度452字节" | `消息长度…字节` |
| ByteOffsetWithinMsg | "字节偏移X" | "自字节偏移72处读取数据集" | `字节偏移\s*\d+` |
| DataSetSize | "数据集大小X字节" | "数据集大小4字节" | `数据集大小…字节` |
| ParameterSize | "占X位" 或 "（X位…）" | "SPEED参数占16位"、"（16位，SINT格式…）" | `占\d+位` / `（\d+位` |
| SDIExpected | 提到 SDI | "当SDI=1时"、"SDI位" | `SDI` |
| SSM | "SSM=XXX" | "SSM=BNR" | `SSM\s*=\s*[A-Za-z]+` |
| FuncRngMax | "满量程范围/功能范围/量程（为）A至B" | "满量程范围为-32768至32767"、"量程-70~1100" | `…范围\s*为?\s*-?\d+…至…` |
| FuncRngMin | 同上 | 同上 | 同上（Max/Min 同时命中） |
| Units | 提到"单位"或常见单位词 | "单位：degrees C"、"12700（RPM）" | `单位…` / `degrees C\|RPM\|°C\|kPa` |
| DataFormatType | 出现数据格式词 | "SINT格式"、"编码格式为DIS" | `BNR\|BCD\|DIS\|ISO5\|SINT\|OPAQUE`（**不加 `\b`**，中文与英文相邻时词边界失效） |
| LsbRes | 提到"分辨率"（或"每bit代表X"），**且不是否定/排除语境** | "分辨率每bit代表1RPM"、"分辨率为0.001" | `分辨率[每bit代表]?[:：为是]?数值`，值取 `1RPM`/`-1V`/`0.5RPM`/`0.001` |
| OneState | 出现 `bitX=1` 取值定义 | "当bit22=1时…有效" | `bit\d+=1` |
| ZeroState | 出现 `bitX=0` 取值定义 | "当bit22=0时…无效" | `bit\d+=0` |
| CodedSet | 出现 `bitX=0/1` 编码定义（0/1 编码集） | "1A时bit8=0,bit9=0；1B时bit8=1,bit9=0" | `bit\d+=\d`（0/1 编码）；**值提取完整编码表**（模式A：通道位置→bit组合；模式C：状态→bit 倒装；模式B：bit条件→状态），信号级接口项按 bit/name 过滤只保留该信号编码项 |
| Name | 提到信号名（多级锚点提取，见下节），或**无具体信号名时提到 A429 固定格式字段** | "为AFTEFAN1速度信号"、"（信号名：风扇速度SPEED）"、"在LABEL的SDI位写入"→SDI | 见「三·补」 |

> 涉及 0/1 编码的需求会同时归入 **OneState、ZeroState、CodedSet** 三类（独立判定，出现即归入）。
> OneState/ZeroState 的值优先由 AI 辅助识别（state_map）覆盖；CodedSet 值提取**完整编码表**
### 关于"注释"字段里的分辨率

FGMC 把分辨率写在 `注释` 字段里（`需求中文` 没有），例如：

| 需求 | [注释] 内容 | 结论 |
|---|---|---|
| `005910` | "乘以1000：分辨率为0.001" | **真属性** → 归入 LsbRes，值 `0.001` |
| `005916` | "接收FRDC发来的燃油温度已经按0.25分辨率扩大，FGMC此处不再做处理。" | **排除性说明** → 不归入（本条需求明确不做分辨率处理） |

两者的区别只在**语境**：后者的"分辨率"处在否定句里。所以 LsbRes 判定加了否定语境检查——
`分辨率` 所在句子（以 。；;! 换行为界）含 `不再/不做/不涉及/无需/无须/不考虑…` 时不算命中。
按句分界而非整段，所以"分辨率每bit代表1RPM；XX信号不再做处理"这种仍是命中的。

> 注意：**"注释"字段是有价值的信息源**（005910 的分辨率就只写在注释里），
> 所以处理方式是"加否定过滤"，而不是把整个字段排除出检测范围。

> （如 HLR_544："bit8=0，bit9=0，通道位置为1A；bit8=1，bit9=0，通道位置为1B；…"），
> 信号级接口项只保留该信号自己的编码项（HLR_547 的 RFAN 标志只含 RFAN 的 bit24 编码）。

> 说明：属性类框架由 `eoicd_crop.yaml` 给出（23 个）。若某属性在需求中确实没被提及，
> 该类为空（`item_count=0`）——这是"提到才归类"的正常结果，不代表规则缺失。

## 三、可调点

所有规则都在 `cluster_hlr.py` 的 `detect_attrs()` 函数里，按需增删：

- **bit 归 DS 还是 Msg**：目前按发送/接收方向拆分。若要统一成一个 BitOffset 类，把两行 `hit(...)` 合并即可。
- **OneState/ZeroState/CodedSet**：目前"出现 bitX=1/0 即归入对应类"。若收紧为"同时出现 1 和 0 才算"，改回 `if m1 and m0` 即可。
- **Name 提取**：锚点分级表 `_NAME_ANCHORS`、尾词表 `_NAME_TAIL_SRC`、噪声词表 `_NAME_PREFIX`/`_NAME_STOP` 均为模块级常量，按需增删（见下节）。
- **新增属性**：在 `detect_attrs()` 里加一条 `hit('属性名', re.search(正则, seg), src)` 即可，属性名须与 eoicd_crop.yaml 中的一致。

## 三·补、Name（信号名）提取算法

各系统需求写法差异很大（"为XX信号""将XX…写入""解析XX""（信号名：XX）"，
以及"直接给下划线式英文名 `RAT_HEAT_FAULT`"），单一动词锚定会大面积漏提。
当前实现是**显式标注 → 英文信号名 → 分级锚点 → 全局兜底**四级：

**第 0 步 · 预处理**：把 `<>`（占位符尖括号）字符替换为空格（保留内容），
避免出现 "缓存>数据接收至<WWS后货仓1指令" 这类把占位符当名字的脏结果。

**第 1 级 · 显式标注**：`信号名：` / `（信号名 XXX）` 直接取值。
> 例："…风扇速度状态消息（信号名：风扇速度SPEED）写入…" → `风扇速度SPEED`

**第 2 级 · A429 固定格式字段**：需求主干是"将/把 …的 `SSM`/`SDI`/`Parity` 置为…"时，name 取该字段名
（这类需求没有具体物理信号，操作对象就是字组成字段）。

> 例：FGMC"OFP软件应将**DISC信号的SSM**置为00" → `SSM`（而不是"…信号"这种泛称）；
> 同 AMS HLR_544"在LABEL的SDI位写入固定数据" → `SDI`。

**第 3 级 · 英文信号名**（下划线式标识符，见「三·补4」）：`RAT_HEAT_FAULT`、`EDP_TCB_STATUS_005`、
`Heater_Group_3_RPDU_ESW_CMD`。很多系统（如 RPDU）不写中文名，直接给英文标识符。

**第 4 级 · 分级锚点**（越靠前优先级越高，级别内按出现位置）：

| 级别 | 锚点 | 适用写法 | 例 |
|---|---|---|---|
| 1 | `中的` | 句中后段的参数描述 | "解析L44**中的**风扇速度" → `风扇速度` |
| 2 | `为` | bit 段 → 信号名定义句式 | "bit10至bit28**为**气压高度" → `气压高度` |
| 3 | `写入`/`解析`/`采集`/`发送`/`接收`/`设为`/`置为`… | 动词后置语序 | "**解析**风扇速度" → `风扇速度` |
| 4 | `将` | 名字前置、动词在后 | "**将**风扇速度…写入" → `风扇速度` |

锚点后取**第一个以信号名尾词结尾的短语**为候选；若候选中途跨越了句子结构（含边界词，如"写入"），
则放弃该锚点、继续尝试下一个。

> **锚点只在主句内查找**（首个"软件应"之后）。条件从句里也常有"状态为 X"这类表述，
> 主句限制可避免把条件取值当信号名（FGMC："当软件工作模式状态为**正常模式**或…" → 不取"正常模式"）。

**第 5 级 · 全局兜底**：扫描全文中所有尾词位置，自尾词向左**反向裁剪**（遇边界词/标点即停），
得到候选名字，**取最长的候选**（长短语更具体："左翼温度传感器故障状态"优于停在"左翼温度"）。

**尾词表**（`_NAME_TAIL_SRC`）：`状态消息｜速度信号｜故障状态｜开关反馈｜供电电压回采值｜速度指令｜
工作模式｜温度选择字｜状态字｜变化率｜架次数｜信号｜反馈｜指令｜标志｜状态｜模式｜字｜值｜电压｜电流｜
速度｜转速｜温度｜压力｜高度｜时间｜日期｜架次｜注册号｜字符｜消息｜信息｜阶段｜密度｜流量`
（组合词在前，保证"状态消息"不被"状态"截断）

> **尾词表宜精不宜多**：尾词是"名词短语的结尾"，而多数这类词也会出现在元数据字段里，
> 盲目扩表容易引入误报。实测：加 `代码` 会让 `[实现方法]手工代码` 被当成信号名；
> 加 `位置` 会让 HLR_544 提取出"根据通道位置"。新增尾词后**务必做 A/B 回归**（见第五节）。

**前置处理**：句首条件引导字 `当`/`若`/`如果` 先剥离（否定环视保护"当前/当时/中间"里的"当"，
否则"当前通道配置状态"会被剥成"前通道配置状态"）。

**清洗**：循环剥离前导噪声词（软件应/应/其中/同时/一次/得到/周期发送/离散量/至…）→ 剥 label 前缀
（`L11压调状态字` → `压调状态字`）→ 去"的"（`RFAN的工作模式` → `RFAN工作模式`）→ 过滤通用词
（发送数据/接收数据/状态消息/测试指令…）→ 长度 < 2 视为无效。

**提取不到就返回 null**（不臆造）。

### AI 辅助识别（可选增强）

正则对语义性强的名字仍有局限，支持用 `--name-map` 覆盖：由 AI 读需求逐条提取信号名，人工确认后
产出 `name_map.json`（`{req_id: 信号名}`，无信号名的需求显式标 `null` 表示"AI 已确认无信号名"），
运行加 `--name-map name_map.json`，Name 属性值优先用它覆盖正则结果，evidence 标注 `[AI辅助识别]`。
交付包已带示例 `name_map.json`。

> 映射文件建议带 `text_hash`（需求中文 md5 前 8 位，格式 `{"req_id": {"value":..., "text_hash":...}}`），
> 脚本会据此检测"需求原文已变但 ID 未变"的情况并提示重新生成映射。

## 三·补2、OneState/ZeroState 的 AI 辅助识别

OneState/ZeroState（bit 取值对应的状态定义）正则难以准确提取，原因：

- **倒装语序**："当标志为'有效'时，bit22=1"（状态在前、bit 在后），正则的"bitX=1…设为…"模式抓不到；
- **一需求多 bit 多状态**：一个需求可能定义多个 bit（如 L11 的 bit22-28 各标志），1 态/0 态因 bit 而异；
- **组合编码**：如 SDI 位编码（"1A 时 bit8=0,bit9=0；1B 时 bit8=1,bit9=0…"）是 bit 组合定义通道位置，
  也属状态信息，但正则只能零散命中"bit8=0/bit8=1"。

因此同样支持**两级**：

1. **正则兜底**（默认）。
2. **AI 辅助识别**（推荐）：AI 读需求逐条提取 1 态/0 态定义，产出 `state_map.json`
   （`{req_id: {"OneState": 定义, "ZeroState": 定义}}`），运行加 `--state-map state_map.json`。
   值非 null → 强制命中并覆盖；值 null → 表示 AI 判定该需求确实无状态定义，从该类移除
   （如纯数值/整字类需求）。交付包已带示例 `state_map.json`（含 SDI 编码的提取示例）。

## 三·补3、信号级拆分（signal_map）

单个需求涉及多个信号时（如同一 L30 字含 BBSOV1 全关/全开两个反馈、L11 含 OFVTRV 与多个风扇
可用标志），应按**信号 Name** 拆分为独立接口项，每个接口项有自己的 label/name/bit/direction，
且 bit 范围、BitOffset 属性值按该信号提取（不再整条需求合成）。

正则难以准确拆分（信号名语义性强、bit 与信号的对应关系需要领域判断），由 AI 辅助完成：

- AI 读需求，把多信号需求拆成接口项列表，产出 `signal_map.json`
  （`{req_id: [{label, name, bit, direction}, ...]}`，格式见 README）；
- 脚本加 `--signal-map signal_map.json`：有记录的需求按接口项逐条输出（BitOffset 值按该项 bit 覆盖），
  无记录的需求回退按 label 级拆分；
- signal_map 为**部分覆盖**（只含多信号需求），一致性校验 missing 不告警、stale/text_changed 告警。

## 三·补4、多系统写法兼容（泛化）

不同主机/系统提交的需求文档写法不一致，工具在以下方面做了兼容。

**已实测的五份需求文档**（风格差异很大）：

| 文档 | 风格特征 |
|---|---|
| AMS《空气管理系统控制器…》 | 中文信号名 + `L214/bit16至bit28` + SDI 定义，字段 `需求中文` |
| RPDU | 大量 `<占位符>`，信号为下划线式英文名，无 label/bit，字段 `需求描述` |
| FGMC | 全英文表头，信号在**条件从句**里，标签用 `Label114`，bit 用"第18到28位" |
| HSCU | 标签/信号都是**助记符**（`LBL_DIS_00_SYS1`/`HYD_1_LO_PRESS`），字段 `需求正文`/`实现方式` |
| 补充测试需求（101 条） | 覆盖 23 属性 × 多写法变体 |

### 1. 表头字段名别名

各系统表头写法不同，解析时统一归一到标准字段名（`FIELD_ALIASES`）：

| 标准字段 | 兼容写法 |
|---|---|
| 需求ID | 需求编号、需求标识、需求条目编号 |
| 需求中文 | 需求描述、需求内容、需求文本、需求名称、需求说明、**需求正文** |
| 基本原理 | 原理、设计原理、实现原理、需求原理 |
| 验证方法 / 实现方法 | 验证方式 / 验证手段、**实现方式** / 实现手段 |
| 对象类型 / 是否衍生 / 安全相关 | 需求类型、衍生、安全性 / 安全等级 |
| 是否为需求 | 是否需求、是否作为需求 |

未识别的字段名原样保留，不影响解析。

> 各系统实测：AMS 用 `需求中文`，RPDU 用 `需求描述`/`需求原理`，FGMC 用 `需求编号`/`需求描述`/`需求原理`，
> HSCU 用 `需求正文`/`实现方式`。

### 2. 需求 ID 格式不限

`FSF21000101_HLR_280`、`FSF24710101A_HLR_052331`、`Test-101` 等都能处理（ID 仅作字符串标识）。
另外，**末尾只有表头、需求 ID 为空的空表格会被自动跳过**。

### 3. 尖括号占位符 `<xxx>`

系统需求常写 `<A664总线数据接收缓存>`、`<RPDU机位号>`、`<MICRO_COMM_A>` 这类占位符——
它们是数据类型/缓存/条件，**不是信号名**。处理方式：

- 中文规则：去掉 `<>` 字符保留内容（这样 `<FCS FCM2空速信号数据缓存>` 仍可提取到 `FCM2空速信号`）；
- 英文名提取：**整段剔除**，避免把 `<MICRO_COMM_A>` 这类位号当信号名。

### 4. 英文信号名（下划线式标识符）

识别形如 `RAT_HEAT_FAULT` / `Heater_Group_3_RPDU_ESW_CMD` / `EDP_TCB_STATUS_005` / `HYD_1_LO_PRESS`
的标识符，自动去噪：

| 情况 | 判断 | 例 |
|---|---|---|
| 在 `<占位符>` 内 | 剔除 | `<MICRO_COMM_A>` |
| 模板占位标识符（含 `XX`/`XXX`） | 剔除 | `LBL_XXX`、`AA_XX` |
| 后接"主应用/软件/分区/模块" | 软件名，剔除 | `MICRO_COMM主应用分区软件` |
| 后接**较长的中文片段**或**含信号类别尾词的中文** | 只是中文名的一部分，交给中文规则整体提取 | `FWD_CED2供电电压回采值` → 不截成 `FWD_CED2` |
| 后接**短中文虚词**（置为/的值/为/时…） | 认定为**独立助记符**信号名 | HSCU：`LBL_DIS_00_SYS1_SSM置为SSM_DIS_NO` → 取 `LBL_DIS_00_SYS1_SSM` |
| 位于"置为/设为/为"之后 | 是**被赋的值**，不是信号 | `置为SSM_DIS_NO` → 取 `SSM_DIS_NO` 作取值 |
| 后接信号类别词（信号/状态/指令…） | 认定为信号名 | `RAT_DEPLOYED信号` → `RAT_DEPLOYED` |

> 判据要点：标识符后若是**短中文且不含信号类别尾词**，说明它本身就是一个完整信号（HSCU 风格）；
> 若是**长中文短语或含尾词**，说明英文只是中文名的前缀（AMS/RPDU 风格）。

### 5. 多信号需求自动拆分

需求以编号/分号列举多个信号时（"数据组成如下：（1）RAT_HEAT_FAULT；（2）RAT_TEST_OK；…"），
**自动按信号拆成独立接口项**（每项独立的 name / direction / bus），无需先做 AI 的 signal_map。

拆分优先级：`signal_map`（AI，最精确） > **自动拆分**（识别到 ≥2 个去重后的英文信号名） > label 级拆分。
可用 `--no-auto-split` 关闭自动拆分。

两条配套规则：

- **标签名不重复计入信号**：标识符若与已识别的标签/助记标签名相同（HSCU "构造并传输 `LBL_DIS_00_SYS1`，其内容如下…"），
  只作标签、不进信号列表；
- **单标签需求自动继承**：需求只涉及一个标签时，拆出的每个信号项都带该标签作为身份
  （HSCU `022587` → 13 个信号项，`label_name` 均为 `LBL_DIS_00_SYS1`、`label` 为 null）。

> 实测：RPDU `052339`（EDP_TCB_STATUS ×6）自动拆成 6 项，`052354` 拆成 9 项；
> HSCU `022587` 拆成 13 项、`023507` 拆成 20 项；单信号需求（如 `052338` → RAT_DEPLOYED）保持 1 项。

### 5·补、条件从句与主句（FGMC 风格）

有些系统（FGMC）把信号写在**条件从句**里、把动作写在主句里：

> 若当前通道配置状态为 `FGMC_CHA`，OFP软件应将所有ARINC 429标签的第9和10位分别设置为"1"和"0"。

处理方式：

1. **句首条件引导字剥离**：`当`/`若`/`如果` 开头的引导字先去掉（用否定环视保护"当前/当时/中间"里的"当"）；
2. **句法锚点限定在主句内**：`为`/`将`/`写入` 等锚点只在主句（首个"软件应"之后）内查找，
   避免把条件里的取值（"状态为**正常模式**"）当成信号名；
3. **兜底全句扫描**：锚点都失败时，仍扫描全句尾词，保证条件从句里的名词也能提取到
   （"当**左翼温度传感器故障状态**为正常时…" → `左翼温度传感器故障状态`）。

### 6. 其他写法泛化

| 项 | 兼容写法 |
|---|---|
| 总线 | 优先认"**X总线**"（如"A664总线"），避免被同句的数据格式描述抢先命中——"按照ARINC429格式…发送至A664总线"判 **A664** |
| 方向 | TX：发送/写入/置入/输出/上报/发布/下发/**传输**；RX：接收/解析/采集/读取/输入/订阅/获取 |
| 周期 | "以100ms为周期"、"以100ms的周期"、"周期为100ms"、"100ms周期"、"每200ms**采样**一次"、**"EOICD中规定的刷新率"**（无具体数值时值留空） |
| bit | ASCII 式 "bit13至bit28"、"bit13~28"；中文序数式 "第13位至第28位"、"**第9和10位**"。**两者基准不同**：`bitN` 本身就是 0-based 直接用；"第N位"是 1-based，转 bit 号要**减 1**，且连续位段自动合并——详见下节「7. bit 位段」 |
| label | **只认数字编号**："L30"、"LABEL126"、"Label114"、"标号126"。名称型助记标签（`LBL_DIS_00_SYS1`）**不是 LABEL 号**，不写入 label（此时 label 为 `null`），另见身份字段 `label_name` |
| 数据格式 | `BNR/BCD/DIS/ISO5/SINT/OPAQUE`，用 ASCII 边界环视——"编码格式为DIS"能命中，`LBL_DIS_00_SYS1` 里的 `DIS` 不误命中 |
| 参数长度 | "占16位"、"参数长度16位"、括号参数表里的"16位"；**裸"第30位"不算参数长度**（区别于 bit 位序号） |
| 章节标题 | 属表外正文，不参与任何提取 |

### 7. bit 位段：0-based 归一 + 连贯合并

需求里写 bit 位置有两种笔法，**基准不同**，不能一刀切：

| 写法 | 基准 | 例 | 转换 |
|---|---|---|---|
| ASCII `bitN` | 本身就是 **0-based**（ICD 里的 bit 号） | "bit13至bit28"、"bit22" | 原样 |
| 中文序数 `第N位` | **1-based**（自然语言的"第 N 个 bit"） | "第13位至第28位"、"第9和10位" | **减 1** → 12-27 / 8-9 |

所以 FGMC 的"第14到29位"→ `13-28`、"第30和31位"→ `29-30`、"第9和10位"→ `8-9`；
而 AMS/101 的 "bit13至bit28" 保持不变。

**连贯位段自动合并**：同一条需求里提到的多个位段，若数值上相邻或重叠，说明描述的是
**同一个连续字段**，合并为一个区间：

> FGMC `005916`："通过 ARINC 429 总线的 Label114 的**第18到28位**，**第29位（符号位）**发送左翼油箱燃油温度"
> —— 18~28 与 29 连在一起（该字段占 18~29 共 12 位），合并 → `17-28`

不连贯的位段各自保留，逗号分隔（如"第18到28位、第30位" → `17-27,29`）。

**防误匹配**："第N" 后面必须紧跟"位"或连接符（`至/到/~/～/—/和/与/、/-`），
所以"第2阶段""第2章"这类序数不会被当成 bit；`bit` 前后加 ASCII 边界，`bitrate` 也不误命中。

## 四、身份信息提取（非聚类维度，仅作标注）

每条需求额外提取 5 个身份信息，用于在类内标注该需求涉及哪个接口。**均只从"需求中文"提取**：

| 身份信息 | 来源 | 示例 |
|----------|------|------|
| bus | **只认需求中文里显式出现的总线关键词**（A825/CAN/风扇CAN、A429/429、A664/AFDX、模拟量/Analog/ADCIN、离散量/Discrete）。**不从章节标题、LABEL 字段名、其他表格字段推断**——需求没写总线就是 null，由匹配阶段按 null 通配处理 | A429 / A825 / Analog / null |
| label | **只认数字编号**：`L\d+` / `LABEL\d+` / `标号\d+`。需求里没有具体编号时为 `null`，**不用助记名顶替** | 36（输出为 `L36`）/ null |
| label_name | 名称型助记标签 `LBL_[A-Za-z0-9_]+`（子字段 `LBL_X_SSM`/`LBL_X_Status` 不算独立标签；模板 `LBL_XXX` 剔除）。仅作附加信息，**不参与 label 判定、也不算身份是否为空** | LBL_DIS_00_SYS1 / null |
| bit | bit 范围，统一归一到 **0-based**：中文序数"第N位"自动减 1、"bitN" 原样；连贯位段自动合并。signal_map 接口项按信号给 | 13-28 / 17-28 |
| name | 信号名（多级锚点提取，见「三·补」；name_map / signal_map 可覆盖；**无具体信号名时可识别为 A429 固定格式字段 SDI/SSM/Parity**） | AFTEFAN1速度信号 / SDI |
| direction | **信号方向**：TX 特征优先（发送数据/发送通道/向X发送/发送周期/**发送**/写入/置入）→ `TX`；RX 特征其次（接收数据/接收通道/**接收**/解析/采集/读取/输入）→ `RX`；都没有 → null。TX 优先是刻意的："接收到ATP测试指令后发送XX"这类需求主体方向是发送，开头"接收到"只是触发条件；"发送风扇状态消息""采集离散量风扇硬件故障状态"等泛化动词也已覆盖 | RX / TX / null |

### 身份信息全空 → 不保留聚类

**判据**：`bus` / `label` / `name` / `bit` **全部为 null**。

这类需求接口项既无法用于后续身份匹配，也聚不出有意义的类（典型：HSCU 里只写"以 EOICD 规定的刷新率
处理 `LBL_XXX`"这类泛化需求，`LBL_XXX` 是模板占位符、未指向具体标签）。

处理方式：**从 `attribute_classes`、`requirements`、去重结果中移除**，但**不静默丢弃**——
单独归档到输出的 `dropped_requirements[]`（含 `req_id` / `req_text` / 原因），并在
`meta.dropped_req_count`、`meta.dropped_item_count` 中给出计数，便于人工复核。

> 注意判据是"全空"：只有 `bus` 有值（如需求提到"429数据"）或只有 `name` 有值的，都会保留。

## 五、回归验证方法（改规则后必做）

各系统写法互相牵制，**改一条规则很容易崩另一处**（本项目多次踩到）。每次改动后按下面的方法验证：

**A/B 对比法**（推荐）：复制一份脚本，把待验证的词/规则改回原样，用同一组文档各跑一遍，逐属性类对比
`req_id|name → attr_value` 的差异集。差异应**恰好等于预期的目标用例**，多出来的就是误报。

```bash
# 1) 生成对照脚本（例：验证新增尾词的影响）
python - <<'EOF'
src = open('hlr_cluster_tool/cluster_hlr.py', encoding='utf-8').read()
old = "r'|...|阶段|密度|流量)')"      # 当前
new = "r'|...|阶段)')"               # 去掉新增词
open('.workbuddy/tmp/noextra.py', 'w', encoding='utf-8').write(src.replace(old, new))
EOF

# 2) 两组各跑一遍，diff 属性类
python hlr_cluster_tool/cluster_hlr.py --docx A.docx --out new.json --name-map "" --state-map "" --signal-map ""
python .workbuddy/tmp/noextra.py      --docx A.docx --out old.json --name-map "" --state-map "" --signal-map ""
```

**回归基线**（每次改动后应保持"身份零差异"；已知的合理变化另行确认）：

| 文档 | 基线 | 允许的变化 |
|---|---|---|
| AMS 真实需求（16 条） | 29 接口项，带 AI 映射 | 无 |
| RPDU（11 条） | 44 接口项 | 无 |
| AMS 补充测试需求（101 条） | 101 接口项 | RefreshPeriod 命中数（"每X采样"类新写法） |
| FGMC（7 条） | 7 接口项 | — |
| HSCU（10 条） | 47 接口项 / 丢弃 1 条 | — |

**建议保留的验证维度**：不只比"身份字段"，还要比 **属性类成员数与 `attr_value`**
（本项目曾出现"身份没变但 Name 的 attr_value 被元数据污染"的情况，只比身份会漏掉）。
